# CAMP2026 VPS RC1 deployment and rollback

Release identifier: `CAMP2026-VPS-RC1`
Local tag: `camp2026-vps-rc1`
Runtime: `INTERNAL_BETA`

## Release boundary

The application archive is generated by `scripts\win\package-camp-vps-rc.cmd`. It contains only the exact committed source and the freshly built `tools/ui-mock/dist` directory. Before creating an archive it requires a clean working tree, builds through `scripts\win\build-product-vps.cmd`, and rejects local runtime paths, databases, and non-empty sensitive environment values.

No default shared-state bootstrap is created for this release: `NOT_CREATED_SAFETY_BOUNDARY`. The existing canonical recovery bundle is deliberately broader than a VPS bootstrap: it includes owner-private state and the mixed AI queue/cache store. Do not copy that bundle or any `.local` directory to a VPS as an initial-state archive.

| Class | Deployment treatment |
| --- | --- |
| Immutable application | Include exact committed source and the INTERNAL_BETA `dist` build. |
| Shared canonical product state | Exclude until an owner approves a store-level, validated export. |
| Owner-private state | Exclude: user workspace, research evidence, feedback. |
| Transient state | Exclude: queue/cache, automation state, local runtime output. |
| Secrets | Exclude. Configure them only in the VPS server environment. |

## Prerequisites

1. Obtain the checked release archive and its sibling `RC_RELEASE_MANIFEST.json`, `RC_RELEASE_MANIFEST.md`, and `SHA256SUMS.txt`.
2. Verify every listed checksum before extraction, for example with `Get-FileHash -Algorithm SHA256`; compare the lowercase digest to `SHA256SUMS.txt`.
3. Install Node `v24.16.0` and pnpm `11.8.0` (the authoritative recorded versions are also in `RC_RELEASE_MANIFEST.json`).
4. Configure a server-owned environment file outside the deployed release directory. `tools/ui-mock/.env.example` is the safe variable template; it contains no values.
5. Bind the service only to the intended private interface/reverse proxy. The default product launcher uses `127.0.0.1`.

## Install and build

1. Extract the application archive into an empty deployment directory.
2. Confirm the source commit matches `git_commit` in `RC_RELEASE_MANIFEST.json` (the archive itself intentionally has no `.git` directory).
3. In `tools/ui-mock`, run `pnpm install --frozen-lockfile --prefer-offline`.
4. From the extracted repository root, run `scripts\win\build-product-vps.cmd`.
5. Start only `scripts\win\start-product-vps.cmd`. Set `CRYPTO_EDGE_PRODUCT_HOST` and `CRYPTO_EDGE_PRODUCT_PORT` in the server environment if a non-default bind is required.

The VPS launcher starts only the product runtime. It must not start a collector, scheduler, automation cycle, provider call, or AI worker.

## Initial-state policy

This RC intentionally starts without a copied shared-state bundle. The deployment owner must select and validate a future store-level bootstrap plan before importing any canonical data. A proposed import must:

1. contain only explicitly approved shared logical stores;
2. exclude all private actor data, feedback, research evidence, AI queue/cache, secrets, and automation scheduling state;
3. validate checksums and schemas before mutation; and
4. have a read-only restore preview and a documented rollback bundle.

## Verification

1. Run `scripts\win\check-product-vps-runtime.cmd` from the deployment directory.
2. Confirm `/api/health` and the frontend respond from the same-origin product server.
3. Confirm the visible runtime reports `INTERNAL_BETA`, not `DEVELOPMENT_DEMO` or fixtures.
4. Confirm that no collector, scheduler, AI worker, provider request, or OpenAI request was launched.
5. Record the manifest, checksum verification, host/port, and operator in the deployment log.

## Ordered owner-gated VPS stages

1. **VPS.1 — deploy application only.** Verify checksums, extract to a clean directory, install locked dependencies, and build. Do not copy a `.local` directory or start a worker.
2. **VPS.2 — verify local same-origin runtime.** Start only `start-product-vps.cmd`, check `/api/health`, `/api/readiness`, `/api/scanner/latest`, and the frontend. Stop it after the check if no operator session is required.
3. **VPS.3 — restore/bootstrap approved shared product state.** This RC has no default bootstrap. Use only a later store-level owner-approved export with validation and restore preview.
4. **VPS.4 — verify AI configuration only after explicit owner authorization.** Add the server-side AI secrets/configuration through the protected environment boundary, keep `CRYPTO_EDGE_AI_WORKER_ENABLED=0`, and make no AI call until a separately authorized smoke test.
5. **VPS.5 — verify one central data operation only after explicit owner authorization.** A one-shot must use the approved owner operation and its normal guards. It must not become a scheduled task.
6. **VPS.6 — enable persistent central automation only after all previous gates pass.** First run the offline scheduler/status/single-flight checks, use the task-registration preview, and require an explicit owner authorization for installation. Confirm `IgnoreNew`, the canonical wrapper, logs, and rollback configuration.
7. **VPS.7 — complete a 24-hour or otherwise owner-agreed bounded operational soak.** Record state, health, errors, source freshness, and automation outcomes.

Only after these stages may a separate task authorize a tunnel/domain, and only after that may a separate task authorize AIKINTEL entry or redirect work.

## Operations and failure handling

- Canonical recovery backups are under `tools/data-poc/.local/product-recovery/backups`; operations reports are under `tools/data-poc/.local/product-recovery/operations`.
- Central automation logs, if and only if automation is later authorized, are under `tools/data-poc/.local/automation/logs`.
- On a failed build, checksum mismatch, health failure, or unsafe state-import result: stop the product process, keep automation disabled, retain evidence, and do not retry with copied `.local` folders.
- Review the latest state through the product’s same-origin health/readiness endpoints and the validated Product Radar. Treat an unavailable or stale state as a product-data condition, not permission to run a provider cycle.
- Do not install a Task Scheduler task, invoke `run-central-automation.cmd`, start the collector, start the AI worker, pass credentials on a command line, or use a public bind before the specific owner gate that authorizes it.

## Rollback package manifest

Before any future state import, create and validate a fresh canonical recovery bundle using:

```text
pnpm --dir tools/ui-mock run recovery:owner backup
pnpm --dir tools/ui-mock run recovery:owner validate --bundle <bundle>
pnpm --dir tools/ui-mock run recovery:owner restore --bundle <bundle> --backup-id <id>
```

The last command is a read-only restore preview unless `--apply` is explicitly supplied; do not use `--apply` in an RC deployment check. Record the bundle id, its manifest checksum, the target release id, the source commit, the exact selected stores, the pre-import product version, the approver, and the restore-preview result. Restore only from a validated owner-approved bundle, never by copying `.local` directories.

To roll back immutable application code, stop the product server, verify the previous release archive checksum, deploy that archive to a clean directory, rebuild with its locked dependencies, then start only `start-product-vps.cmd`. Keep state imports separate from code rollback.
